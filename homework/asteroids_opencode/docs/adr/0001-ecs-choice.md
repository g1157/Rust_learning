# ADR 0001: ECS框架选择

## 状态
Proposed

## 上下文
项目正在从传统OOP架构迁移到ECS架构，以提高性能和可维护性。我们需要选择合适的ECS框架。

## 决策
选择 **hecs** 作为ECS框架。

## 理由
- **轻量级**：API简单，学习曲线平缓
- **性能优秀**：零成本抽象，内存布局优化
- **Rust原生**：充分利用Rust类型系统
- **活跃维护**：社区活跃，文档完善
- **适合游戏**：专为游戏开发优化

## 备选方案
- **legion**: 更复杂，调度系统强大，但学习成本高
- **specs**: 老牌框架，生态成熟，但API较旧
- **Bevy ECS**: 功能最全，但依赖Bevy整个生态

## 后果
- **正面**：性能提升，代码更清晰，易于扩展
- **负面**：需要重构现有代码，短期开发效率降低
- **风险**：迁移复杂度，需要Spike验证

## 实施计划
1. 创建hecs Spike验证基本功能
2. 逐步迁移核心系统（移动、渲染、碰撞）
3. 性能基准测试确保FPS不下降
4. 完整迁移后删除旧代码

## 验收标准
- 5000+实体时保持60FPS
- 内存使用不超过原架构20%
- 代码行数减少30%
- 编译时间增加不超过50%
