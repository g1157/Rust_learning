# ADR 0001: ECS框架选择

## 状态
**Accepted** (2024-01 更新)

## 上下文
项目正在从传统OOP架构迁移到ECS架构，以提高性能和可维护性。我们需要选择合适的ECS框架。

经过 spike 验证：
- `spike/bevy_test/`: Bevy 被 libudev 依赖阻塞，不适合当前环境
- `spike/macroquad_spike/`: 简单 ECS 概念验证成功（World + Vec + 系统函数）

## 决策
采用 **渐进式迁移策略**：

1. **短期 (Phase 1)**: 保持当前结构体方案，专注网络预测实现
2. **中期 (Phase 2)**: 试点引入 **hecs** 处理子弹/粒子等高频小对象
3. **长期 (Phase 3)**: 根据试点结果决定是否全面迁移

## 理由
### 选择 hecs 而非其他框架
- **轻量级**：API简单，学习曲线平缓，WASM 体积增加可控
- **性能优秀**：零成本抽象，内存布局优化
- **WASM兼容**：无原生依赖，适合跨平台
- **网络友好**：组件化状态便于快照/序列化

### 渐进式而非一次性迁移
- 降低风险：避免双轨状态混乱
- 保持交付节奏：不阻塞网络功能开发
- 验证收益：用试点数据证明 ECS 价值

## 备选方案
- **legion**: 更复杂，调度系统强大，但学习成本高
- **specs**: 老牌框架，生态成熟，但API较旧
- **Bevy ECS**: 功能最全，但 libudev 依赖阻塞
- **保持 OOP**: 零迁移成本，但扩展性受限

## 后果
- **正面**：性能提升，代码更清晰，网络快照更简洁
- **负面**：试点期间代码复杂度略增
- **风险**：试点失败需回退，已通过 spike 降低

## 实施计划
### Phase 2 试点范围
1. **子弹模块** (Bullet) - 高频创建/销毁，生命周期简单
2. **粒子系统** (Particle) - 纯视觉，无网络同步
3. **道具模块** (PowerUp) - 简单组件，有网络同步需求

### 迁移顺序
```
Bullet → Particle → Asteroid → PowerUp → (评估) → Player
```

### 网络同步考虑
- 定义 `NetSnapshot` 组件视图（仅同步必要字段）
- 保持 serde/bincode 兼容
- 客户端预测标记本地控制实体

## 验收标准
- 5000+实体时保持60FPS
- WASM 体积增加 < 100KB
- 试点模块单元测试覆盖率 > 80%
- 网络快照序列化无回归
